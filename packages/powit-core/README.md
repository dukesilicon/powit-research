# @thoth/powit-core

An in-memory PoWit v0 initial-finalization kernel. It accepts an injected authoritative clock, processes the event action journal, freezes the initial input set, derives admission and the event-specific relation graph, evaluates sufficiency and `EXACT_MATCH`, then emits a canonical Attestation. `replayEvent(bundle)` reprocesses every recorded action and compares the resulting records and claimed outputs. `verifyAttestation(bundle, attestation?, hash?)` returns a structured validity result and reason codes. The core uses Node SHA-256 and RFC 8785 JSON serialization with the v0 safe-integer restriction.

From the repository root, run `pnpm --filter @thoth/powit-core test` for the [normative H01–H20 and E2E vectors](../../protocol/powit/v0/POWIT_V0_TEST_VECTORS.md), the five-participant local execution and adversarial cases. Run `pnpm --filter @thoth/powit-core typecheck` for TypeScript checking and `pnpm build` for compiled JavaScript. [SPEC](../../protocol/powit/v0/POWIT_V0_SPEC.md) and [TYPES](../../protocol/powit/v0/POWIT_V0_TYPES.md) remain the authority.

The package does not implement transport authentication, production identity assurance, storage, a database, APIs, ZK, wallets, settlement, correction governance (B05) or evidence authentication (B06). It consumes upstream assertions and verified-claim states as policy-pinned inputs; it does not establish the underlying human or issuer claims.

## Specification gaps exposed by implementation

- `EventSchema.requiredClaims` names required claim types but the frozen v0 documents do not specify the exact eligibility test for a nonempty list (verification state, accepted policy and missing-value behavior). The kernel rejects nonempty `requiredClaims` with `UNSUPPORTED_POLICY`. Relation claims in the normative fixtures remain supported because `requiredClaims` is empty there. An ADR and vectors must define the missing rule before this shape can activate.
- The timing policy has an `allowObservationCommitOverlap` switch, while v0 also requires report submission at commitment acceptance inside both windows. The `false` case therefore has no admissible commitment time under the stated rules. The kernel rejects that policy with `UNSUPPORTED_POLICY` pending a normative resolution; the fixture profile uses `true`.
- The wire format requires `IntakeDecision.recordRef` for accepted reveals but does not prescribe its value. The local producer uses `reveal-<participationId>`; replay accepts any valid recorded Id for that reference and compares the rest of the action and RevealRecord. A caller may supply an explicit reveal reference. This does not change the candidate Observation or its commitment.
- Invalid lifecycle transitions and malformed disqualification inputs have no frozen rejection reason code or policy-defined code registry. The kernel throws a `ProtocolError` for those cases rather than recording an invented `IntakeDecision` code. Accepted lifecycle and disqualification actions, and the frozen core rejection codes, are journaled and replayed. A follow-on normative decision is needed to make those rejected attempts interoperable.
